# GitHub touchpoints and the typed GH service methods they need

Inventory for #868. It records every place maintained PDB code reaches GitHub, directly or through a wrapper, and proposes the typed asynchronous service method each caller should use instead. It is an input to the GH service contract; implementing the service and migrating callers are separate tickets. Source: `main` at 07a7e7c (2026-11-17).

## How this was found (reproducible)

Run from the repository root:

```sh
# 1. Every process-execution site and every module importing child_process (production only).
grep -rnE "\b(spawn|execFile|execFileSync|spawnSync|execSync)\(" src scripts --include='*.ts' | grep -v '\.test\.ts'
grep -rln 'node:child_process' src scripts --include='*.ts' | grep -v '\.test\.ts'
# 2. Which of those execute gh (the rest run git or node).
grep -nE '"gh"' src/github/github.ts src/github/ghauth.ts src/github/dependencies.ts src/workflow/issuecreate.ts src/config/localdoctor.ts
# 3. Exported gh wrappers and their consumers.
grep -rnE '^export (const|async function|function) gh[A-Za-z]*' src --include='*.ts' | grep -v test
grep -rln 'ghQueryWith\|ghQuery\b' src --include='*.ts' | grep -v test
grep -rn 'ghRestWith\|ghRest\b' src --include='*.ts' | grep -v test
# 4. Write shapes: gh issue subcommands, label/assignee flags, GraphQL mutations, REST writes.
grep -rnE '\[\s*"issue",\s*"(comment|edit|close|reopen)"' src --include='*.ts' | grep -v test
grep -rnE '"--(add|remove)-(label|assignee|blocked-by)"' src --include='*.ts' | grep -v test
grep -rnE 'mutation\(' src --include='*.ts' | grep -v test
# 5. REST paths.
grep -rnoE '`/?(repos|rate_limit|user)[^`]*`' src --include='*.ts' | grep -v test
```

`src/config/config.ts` (`nodeGit`) and `src/updates/checkout.ts` import `child_process` but run `git`, not `gh`; they are out of scope. `scripts/` helpers that run `node`, `git` or the built CLI (`ci-step.ts`, `smoke.ts`, `package-test.ts`, `test-report.ts`, `datalog-trial.ts`, `benchmark-isolation.ts`, `formal-comprehension.ts`, `website/process.ts`) do not call GitHub.

## Shared method groups (candidate migration tickets)

1. **Transport core:** one typed GraphQL and REST executor behind B1, B2 and B4, preserving `--include` evidence, attempt telemetry, abort, timeouts, buffer limits, quota classification and the read meter. Unify B1 and B4, which today have different buffer and timeout settings; that difference must be deliberate or removed.
2. **Account and repository context:** `account.current`, `account.rateLimits`, `repos.get`, `repos.resolveFromCheckout`, `repos.defaultBranch`, `repos.permissionOf`, `repos.requiredChecks`.
3. **Issue and PR reads:** snapshot and changes, focused and batched gets, locate, timeline, guard fingerprint, PR progress and review history.
4. **Dependencies:** get, page, add and remove.
5. **Comments:** `comments.create` with the #345 recovery and receipts as part of the method, not left to callers; receipt lookup stays internal.
6. **Labels and assignees:** list, exists, create, edit (add/remove) and assignees.add, with observed-state receipts.
7. **Issues:** create and close.
8. **Commits:** `containedIn` (compare).
9. **Local diagnostics (non-API):** gh version and auth status for doctor; kept separate from the GitHub service.

## Findings for the service contract

- **Raw argv crosses module boundaries today.** Seven workflow modules build `gh issue …` argument arrays as plans (`command: [...]`), which `ghRun` executes. The plan/apply split is worth keeping, but a plan should hold a typed operation (for example `{ op: "labels.edit", add, remove }`), not gh argv.
- **Two GraphQL executors.** `ghQueryWith` (B1) and `ghGraphqlApi` (B4) both run `gh api graphql` with different limits and error handling. A single executor should own both reads and mutations.
- **Mixed transports for the same capability.** Comments are created through REST (B7) and GraphQL (`addComment` in estimate); labels through `gh issue edit` (B6) and GraphQL mutations (estimate). The service should expose one method per capability and choose the transport internally.
- **Non-API steps stay explicit.** `currentRepository` depends on local git remotes and gh configuration, and doctor probes the gh binary itself. Neither maps to a single API call; both should remain explicitly local operations.
- **Unconfirmed mapping.** `gh issue edit --add-blocked-by/--remove-blocked-by` is used for native dependency writes, but the exact API call gh makes isn't established from this repository. Confirm it from gh's source or recorded traffic before writing `dependencies.add/remove`.
- **Test boundaries are already injectable.** `Query`, `Rest`, `GraphqlApi`, `GhRun`, `RestPost` and `Spawn` are injected throughout the tests, so migrations can swap callers to service methods without new test infrastructure.
